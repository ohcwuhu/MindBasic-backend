# 卡片知识库接入说明

> 2026-10-01。本文说明平台侧卡片知识库如何自动生效，
> 以及为什么**不需要**把知识库导入 Dify。

---

## 一、结论先说

- 检索在**平台侧**完成，结果通过 Dify 开始节点的 `knowledge_context` 变量传入工作流。
- 知识库文件随代码发布在 `knowledge_base/`，**后端首次检索时自动构建索引**。
- 使用者不需要跑构建命令，也不需要在 Dify 里建数据集、上传文件。
- 旧的整本书检索方案（`kb_service.py`）已于 2026-10-01 **整体下线**，代码已移出仓库。

## 二、一轮对话里的位置

1. ASR 得到文本后，并发启动两件事：多模态情感分析，以及知识库索引预热。
2. 风险分级得到 `risk`（NONE / LOW / MEDIUM / HIGH）。
3. 五阶段引擎得到 `stage`（opening / exploration / goal_setting / action_planning / closing）。
4. `kb_cards.context_block(asr_text, stage=..., risk=...)` 在本地做检索：
   - 寒暄短路：招呼语直接返回空；
   - 风险硬过滤：`risk >= MEDIUM` 时只放行 L0 安全卡；
   - 阶段软降权：阶段不匹配的卡片分数乘 0.6；
   - 门限：低于 `min_score` 不注入。
5. 结果作为 `knowledge_context` 传给 Dify 开始节点，提示词里直接引用。

检索全程是本地 jieba + BM25，**不调用任何模型**，毫秒级。
因此不再需要旧方案里"用并发隐藏 2~4 秒 DeepSeek 调用"的技巧；
索引预热仍然并发执行，避免进程首次调用时的 0.8 秒构建落在关键路径上。

## 三、文件清单

| 路径 | 作用 |
| --- | --- |
| `knowledge_base/` | 卡片本体（68 张参与检索 + 2 个导航文档） |
| `app/services/ai_lab/kb_cards.py` | 卡片解析、索引构建、检索、过滤 |
| `data/kb_cards_index.pkl` | 自动生成的索引（被 `.gitignore` 忽略，不需要提交） |
| `scripts/sync_kb_cards.py` | 把编辑目录的改动同步到 `knowledge_base/` |
| `tests/test_kb_cards.py` | 12 个单测，锁定解析、过滤、降级与自动重建 |
| `socket_events.py` | 并发预热索引；拿到阶段与风险后检索并注入 `knowledge_context` |
| `Dockerfile` | 新增 `COPY knowledge_base ./knowledge_base`，保证镜像内自带卡片 |

## 四、改卡片之后怎么生效

卡片在 `项目主体/心理教练知识库-自建/` 里编辑，运行时读的是
`MindBasic-backend/knowledge_base/`。同步一条命令：

```bash
cd 项目主体/项目代码/MindBasic-backend
python scripts/sync_kb_cards.py
```

脚本会同步文件并重建索引。**即使忘了跑这个脚本**，只要直接改了
`knowledge_base/` 下的文件，后端下次检索时也会通过文件指纹发现变化并自动重建。

只想看差异不动文件：

```bash
python scripts/sync_kb_cards.py --dry-run
```

## 五、可调参数（环境变量）

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `KB_CARDS_DIR` | `<backend>/knowledge_base` | 卡片目录 |
| `KB_CARDS_INDEX` | `<backend>/data/kb_cards_index.pkl` | 索引文件位置 |
| `KB_CARDS_TOP_K` | `2` | 每轮注入卡片数。实测 top-1 精准，top-2 之后开始稀释 |
| `KB_CARDS_MIN_SCORE` | `5.0` | 相关性门限，低于则不注入（在 50 条评测集上标定） |
| `KB_CARDS_STAGE_PENALTY` | `0.6` | 阶段不匹配时的降权系数 |

## 六、阶段与风险取值

- **阶段**：平台 `coach_stage_service` 用英文枚举
  `opening / exploration / goal_setting / action_planning / closing`，
  卡片为了给人读用中文 `建立 / 探索 / 目标 / 行动 / 收束`。
  `kb_cards.normalize_stage()` 负责两边对齐，两种写法都能匹配。
- **风险**：`NONE / LOW / MEDIUM / HIGH`，与 `crisis_rules` 一致。

## 七、自检

```bash
# 构建并看统计
python -m app.services.ai_lab.kb_cards build

# 不套门限看全部候选分数
```

## 八、已下线的旧方案

2026-09-23 的方案是把 15 本书的正文切块入索引，用 DeepSeek 做查询扩展与重排。
它解决的是"能不能检索"，没有解决"检索到的东西能不能直接用"——实测 6992 个片段里
18.8% 是目录与 OCR 噪声，命中单位是作者的论述段落。

卡片知识库把命中单位换成"一个场景 → 一个动作 → 一组话术"：Recall@4 从 75% 提升到 100%，
噪声降到 0，且不再产生模型调用费用（详见 `心理教练知识库-自建/_工具/评测报告.md`）。

**2026-10-01 该方案整体下线**。以下文件已移出仓库，备份在
`斐思同行/_retired/2026-10-01-整本书知识库下线/`：

| 已移出仓库 | 说明 |

| `app/services/ai_lab/kb_service.py` | 整本书检索实现 |
| `scripts/build_kb_index.py` | 旧索引构建脚本 |
| `tests/test_kb_service.py` | 旧模块单测（6 项） |

## 九、Dify 侧要做什么

**什么都不用做。** 工作流开始节点已经声明了 `knowledge_context` 变量，
提示词里也已经引用它。平台会把检索结果填好再调用工作流。

唯一可选动作：工作流里那个 `知识检索` 节点目前是断头节点（输出没接到生成节点），
它指向的是 Dify 侧的数据集。既然检索已经在平台侧完成，可以把它删掉——
但删除需要重新导入工作流，属于可选清理，不影响本次接入。
